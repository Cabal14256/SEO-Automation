# M3 实物箱核对与确认开发方案

> 历史阶段计划：保留编写当时的设计、安排和判断，不作为现行功能或操作说明。当前范围见[实现状态](../../development/implementation-status.md)、[业务规则](../../business/rules.md)与[运行维护](../../operations/runbook.md)；同目录背景见[历史索引](../README.md)。新发票不再以 M3 实物箱整组确认为前置条件，外部业务操作继续由人员执行。

> 历史方案。2026-10-23 用户取消实物箱确认功能，工作区入口及新发票 M3 门槛已移除；下文描述旧功能、历史数据和兼容维护规则。当前发票直接取领星/M2 逐箱数据并允许本票修改，见[当前箱规规则](../../business/invoice-box-data.md)。

> 2026-10-19 入口调整：本文早期“五步批次向导”方式由《M2／M3／M4 历史拆分计划》替代。M2 保持四步制表且不查询 M3；M3 位于“发货管理 → 实物箱确认”。旧 physical 深链接及保存阶段进入独立任务，数字第 4 步仍为发货表导出。本文取值、草稿、整组确认、版本和三表导出规则继续有效，真实现场签收仍待完成。

## 一、交付目标与已确定规则

在现有发货批次中增加“逐箱核对 → 整组确认 → 实物箱明细导出”流程，供有效管理员操作。

| 项目 | 本期规则 |
|---|---|
| 数据来源 | 以领星登记重量、箱规和 Reference ID 为准，保留原始值、单位及来源 |
| 重量口径 | 采用毛重；现场核对记录独立保存 |
| 数值处理 | 统一转换为 KG、CM，再四舍五入到两位小数，中间计算不截断 |
| 现场录入 | 一致时勾选即可；有重量尺寸差异时填写实测值和原因，最终仍采用领星值 |
| 缺项处理 | 必要重量、尺寸或 Reference ID 缺失时阻止 M3 确认，回领星补齐后显式同步 |
| 确认范围 | 逐箱保存核对进度，全部箱完成后整组确认 |
| 数据变化 | 采用实质变化的新版本后，整组清除核对勾选并重新确认 |
| 货箱编号 | `FBA号 + "000001-" + 该FBA实际箱数`，箱数按内部箱 ID 去重 |
| PO Number | 对应 FBA 的 Reference ID |
| 本期输出 | 标准实物箱明细 XLSX；完整示例物流商 B2B 文件留到后续单据模块 |

现有 M2 发货表继续按原规则导出。M3 状态、确认和导出条件独立管理，全流程保持领星只读。

## 二、后端、数据与接口

### 独立保存 M3 事实

新增五类记录：领星来源采集任务、来源快照、实物核对修订、实物确认、实物明细导出。复用现有认证、事务幂等、文件存储、审计及 Worker。

- 每个核对修订绑定一个 M2 确认 ID，并按“货件修订 ID＋内部箱 ID”关联实际箱。
- 保存领星原值、换算值、逐箱核对结果、实测差异、原因、操作人和时间；修订与确认均追加保存。
- M3 使用独立版本号，不修改 M2 的确认版本、箱码或冻结快照。
- 历史批次默认“未完成实物确认”，不根据已有 API 数据自动补成已确认。

### 独立采集领星来源

M3 同步复用现有领星客户端、限流、请求预算和快照存储，但使用独立任务，**不发布 M2 商品箱候选**。现有普通同步会新增商品修订，直接复用可能使未冻结的 M2 确认过期。

- 打开页面只读取已有证据；用户点击同步才请求领星。
- 历史 Reference 优先从绑定修订的可信原始快照解析，核验文件哈希、店铺和 FBA；不从全库最新记录静默拼接。
- 新采集结果必须逐箱匹配身份、完整商品标识和箱内数量。
- 重量、尺寸或 PO 更新可作为新 M3 来源；箱身份、商品或数量不符时阻止采用，进入现有 M2 映射／更正流程。
- Reference 两个来源不一致时列为阻塞项，回源核对，不自动任选一个。

### 新增接口

以 `/api/v1/sub-batches/:id/physical-review` 为前缀：

| 接口 | 用途 |
|---|---|
| `GET /`、`GET /history` | 当前底稿、状态及修订／确认历史 |
| `POST /sync`、`POST /sources` | 显式采集、核对并采用指定来源 |
| `POST /revisions` | 保存逐箱勾选和实测差异草稿 |
| `POST /confirmations` | 整组最终确认 |
| `GET /template.xlsx`、`POST /intake` | 下载核对模板、预检及提交批量核对结果 |

另增 `POST /api/v1/physical-exports` 创建导出任务，`GET /api/v1/physical-exports/:id` 查询结果；下载复用现有授权文件接口。

写操作绑定 `operationId`、M2 确认 ID、期望 M3 版本和来源指纹。服务端计算采用值与差异，不接受客户端覆盖领星来源；版本冲突返回 409，校验阻塞返回 422。

## 三、页面与标准明细

### 加入现有批次流程

处理向导调整为：

**分组与成员 → 同步与商品 → 制表确认与编码 → 实物箱确认 → 成品与导出**

- M2 条件满足后可直接进入成品步骤，未完成 M3 时仍可导出原发货表。
- 步骤完成标记依据真实业务状态，跳过实物步骤不会显示其已完成。
- 批次详情增加“实物箱确认”，与向导复用同一组件。
- 一箱一行展示 FBA、内部码、箱序、PO、范围箱号、领星重量尺寸、KG/CM 采用值、来源时间及核对状态；箱内商品展开查看。
- 选择“有差异”才展开实测输入与原因。“一致”仅记录核对事实，不复制领星值伪造实测记录。
- 保存草稿后可刷新、退出或换电脑恢复；未保存输入仅在当前标签页暂存。后台刷新不覆盖编辑内容。

旧向导数字步骤迁移为带版本的语义阶段，原第 4 步明确映射至“成品与导出”。保留旧深链接，新增 `physical` 标签入口。

### 两种导出分开显示

“成品与导出”提供独立按钮和历史：

- **发货表 XLSX**：沿用 M2 条件。
- **实物箱明细 XLSX**：要求当前有效 M3 整组确认。

M3 文件包含三张表：

1. **实物箱明细**：一箱一行，包含 PO、范围箱号、内部码、采用重量尺寸、实测差异及核对信息。
2. **箱内商品**：逐箱商品身份与数量，避免重复汇总箱重。
3. **版本与核对记录**：M2/M3 确认、来源时间、规则版本、确认人和时间。

重量尺寸写入数字单元格，格式统一 `0.00`。批量核对模板只接受核对结果、实测值及原因；提交时重新检查文件哈希、箱身份和版本，任一行错误则整次拒绝，不覆盖 API 数据。

## 四、确认、变化与兼容规则

- 最终确认要求：M2 确认有效、箱码齐全、逐箱身份和数量一致、领星必要字段有效、全部箱已核对、所有重量尺寸差异均有实测值及原因。
- 重量尺寸差异按转换后的两位小数比较，不另设容差；商品或数量差异不能通过备注豁免。
- 业务指纹包含箱成员、商品数量、两位 KG/CM 值、Reference 和缺项状态，排除任务 ID、采集时间等元数据。等值重采不清除核对进度。
- 发现实质变化时暂停新的 M3 确认和导出；用户采用后创建新修订并整组重核。旧确认、差异记录和文件保留。
- 核对中的正常勾选和差异填写保存为草稿修订；已确认后修改实测记录，则原确认过期并要求整组重新核对。
- 已冻结、未被替代的 M2 批次允许追加 M3 记录；成员和商品数量更正仍走原更正组流程，被替代旧组只读。
- M3 首次正式导出成功时沿用批次冻结机制。排队与发布前均复核版本，过期任务标记失效，生成失败不提前冻结。
- 请求失败、查无货件与字段为空分别提示；失败保留此前成功数据，重试保持原操作号，不自动补零或虚构 PO。

## 五、实施顺序与验收

1. **契约与迁移**：建立 M3 数据、接口和状态契约；验证增量迁移及历史兼容。
2. **来源与计算**：完成可信快照解析、独立采集、箱身份比对、Reference 映射、单位换算及指纹。
3. **核对与确认**：完成草稿、批量导入、差异处理、整组确认、失效判断和事务幂等。
4. **页面与导出**：接入五步向导、详情、双导出入口、历史及标准 XLSX。
5. **技术与业务验收**：先使用归档样本和隔离夹具验证，再用一个真实批次逐箱核对并明确签收。

重点验证：

- KG/LB、CM/IN 换算、四舍五入边界及页面/XLSX 两位小数一致。
- 缺值、非法值、未知单位、Reference 缺失／冲突不能误报完整。
- 混装、商品跨箱、不同箱规及超过十箱仍逐箱准确，范围编号不重复计箱。
- M3 同步不新增 M2 候选、不影响原发货表导出条件。
- 同内容重采不失效；实质变化、并发修改、重复提交和响应丢失均保持正确版本。
- 冻结批次补做 M3、旧步骤恢复、历史文件下载和导出期间版本变化。
- 桌面及窄屏表格、键盘操作、草稿恢复和网络失败提示。

交付标准是：管理员能完成整组逐箱核对，保存可追溯的独立实物确认，并导出与该确认版本一致的标准明细。
