# M2/M3/M4 正式部署建设方案

日期：2026-10-19（Asia/Shanghai）

## 1. 方案结论

首期正式环境采用**单台 Windows 主机、局域网 HTTPS 访问**。主机运行 PostgreSQL、Hono API、独立任务 Worker 和 HTTPS 反向代理；API 与数据库仅监听本机回环地址，浏览器只访问 HTTPS 入口。React/Vite 构建产物由 API 提供，上传文件、生成的 XLSX、模板和业务证据放在源码及发布目录之外的持久化 `DATA_DIR`。

该方案沿用仓库已有的 Windows 试用发布、服务托管、健康检查、发布校验及加密备份恢复实现。正式环境必须独立于开发和试用环境，使用独立数据库、文件目录、服务标识、凭据和发布目录。试用环境可用于验收，不直接改造成生产环境，也不把试用数据库直接作为生产数据源。

本文用于确定部署建设路线，不代表生产主机已经采购、配置或验收。目标机具体规格、生产访问地址、证书、备份介质及恢复目标须在投产前完成确认。

## 2. 文档要求与部署决策

### 业务计划明确要求

《M2+M3+M4 PLAN.md》规定 M2 发货表、M3 实物箱核对和 M4 发票单据是独立工作任务；M2 导出不依赖 M3 完成状态，M4 生成待复核发票则要求来源组有当前有效的 M2 确认、箱码和 M3 整组确认。M4 首期输出 XLSX，来源、资料、模板、修订、复核和生成文件须版本化保存。

计划要求沿用 `/api/v1`、管理员认证、事务幂等和版本检查；复用现有 Worker、文件存储、发布及授权下载机制；生产数据使用增量迁移，备份和恢复覆盖新增资料、单据及文件引用。生成或发布前复核依赖版本，发布成功后才冻结来源组；失败不得提前冻结。业务验收包括自动回归、文件视觉检查、接收系统实际导入和人工签收。

计划没有指定正式主机操作系统、服务器规格、数据库高可用方式、证书来源、网络拓扑、备份介质、RPO/RTO 或监控产品。

### 本方案的工程决策

首期选单机 Windows，是基于当前仓库已有 Windows 服务化部署和恢复实现作出的建设建议，不是业务计划的明文规定。单机方案适用于当前首期工作量；部署验收沿用最多 5 个会话、至少 1000 箱代表数据的性能测试目标。该目标是待实测验收值，不等同于已经达到的容量承诺。

保留 PostgreSQL 作为唯一业务数据库，沿用当前 Node.js 24、pnpm 锁文件、Drizzle 迁移和 pg-boss 持久队列。M4 增加的单据、成员、来源快照、资料档案、模板版本、修订、复核、生成任务及文件索引都进入同一数据库和 `DATA_DIR` 备份边界。

## 3. 目标运行架构

```text
局域网管理员浏览器
        │ HTTPS / 固定内部域名
        ▼
受信任 HTTPS 入口（Caddy 或组织标准反向代理）
        │ localhost
        ├── Hono API + React/Vite 静态构建产物
        ├── PostgreSQL 18（本机服务，仅本机监听）
        └── 独立 Node.js Worker（pg-boss 队列）

持久化 DATA_DIR ── 上传原件、导出 XLSX、模板和文件索引引用
独立备份介质 ──── 加密备份、恢复密钥独立托管
```

- API、Worker、PostgreSQL、HTTPS 代理分别作为受管 Windows 服务运行，配置自动启动、故障重启和受控日志轮转。服务使用权限受限的服务身份；数据库及 API 端口不向局域网开放。
- 生产入口使用固定内部 DNS 名称和组织信任的 TLS 证书。试用环境的本机内部 CA 只适用于试用验收，不能假设其他客户端已信任。
- 防火墙仅开放获准客户端到 HTTPS 端口的访问。PostgreSQL 使用本机监听和强认证；服务端密钥、数据库密码、领星凭据和 TLS 私钥通过受控配置及 Windows ACL 管理，不放入源码或发布包。
- 领星保持只读集成，外部请求仅在业务人员显式触发并确认授权预算后启用。验收和恢复副本固定 `LINGXING_REQUESTS_ENABLED=false`；恢复核对未决任务后再由负责人决定是否恢复 Worker 任务。
- 生产、试用/验收、开发使用不同数据库、`DATA_DIR`、端口、凭据、证书配置和服务名。恢复演练在隔离目标中进行，禁止连接生产领星凭据或触发外部业务请求。

## 4. 发布与数据库变更

1. 从受控源码版本构建不可变发布包，使用锁文件安装依赖，并运行类型检查、lint、单元/集成测试、生产构建和 M2/M3/M4 相关验收。发布包应包含 API、Worker、Web 静态资源、Node 运行时、迁移、必要模板及逐文件校验清单；排除业务原件、生产配置、密钥和数据库。
2. 在隔离验收环境用归档样本和夹具验证迁移、API/Worker 健康、授权下载、任务重试、生成文件及恢复。通过后再把同一发布包晋级到生产，避免在目标机直接构建不同产物。
3. 维护窗口开始前确认无进行中的同步、导出和人工确认操作；停止 API/Worker 写入，生成并校验数据库与 `DATA_DIR` 的升级前完整加密备份。
4. 应用向后兼容的增量 Drizzle 迁移，再启动新版本 API 和 Worker。检查 `/api/v1/health`、数据库连接、实际 Worker 进程及新心跳、关键页面登录和授权文件下载；执行受控 XLSX 生成及内容/哈希抽查。
5. 迁移期间或健康检查失败时停止新版本服务并保留现场日志。应用启动失败可切回上一不可变应用版本，但数据库迁移不能靠切换代码自动逆转。若迁移不兼容或数据结构无法安全复用，应把升级前完整备份恢复到隔离的新数据库和文件目录，核对通过后再切换服务；不得对原数据库执行未经验证的破坏性降级。
6. M4 发布时再次校验来源 M2/M3 确认、商品与箱身份、资料和模板版本。只有文件发布成功后才执行计划规定的来源组冻结；任务失败不得冻结或重复占用货件。发票文件经系统下载后如有 Excel 手工修改，须回系统建立修订、重新生成和复核。

## 5. 数据保护与恢复

正式备份作为一个可恢复集合，至少包括 PostgreSQL、完整 `DATA_DIR`、文件索引及哈希引用、Drizzle 迁移、模板和规则、应用发布版本、受控运行配置，以及恢复所需的密钥材料。备份文件加密；备份介质与生产主机分离，恢复密钥单独托管，不与备份包同处一地。

建议每日备份并至少保留最近 30 天，按月在隔离环境恢复。该频率和保留期沿用现有运行维护基线；仓库试用环境目前写入同机暂存，不能作为正式独立备份通过。新建 M4 资料、单据、历史 XLSX、文件索引及其版本引用必须纳入同一备份恢复验证。

恢复流程先恢复到隔离目录和独立数据库，默认不启动 Worker、不启动领星请求；核对业务表和序列、管理员登录、审计和确认记录、未决任务、文件哈希、历史 XLSX 及 M2/M3/M4 版本引用。负责人审查未决操作后，才允许按任务类型逐项恢复。

恢复目标暂定如下，须由业务负责人批准并通过独立介质演练后才能作为正式服务承诺：

| 指标 | 建议基线 | 确认方式 |
| --- | --- | --- |
| RPO | 以每日成功备份为基础，目标不超过 24 小时 | 记录备份时间、故障时间及恢复点年龄；确认业务可接受的数据窗口 |
| RTO | 上线前由业务负责人确定 | 至少一次从独立介质完整恢复并记录从故障确认到业务可用的耗时 |
| 留存 | 最近 30 天每日成功备份 | 自动检查备份完整性、加密校验及过期清理结果 |
| 演练 | 每月一次隔离恢复 | 核对数据库、文件哈希、历史 XLSX、账号和未决任务；留存报告 |

每日备份本身不证明 RPO，单次本机恢复时间也不证明 RTO。两者以目标设备、独立介质和真实数据的重复演练结果为准。

## 6. 安全与运行监控

- 系统沿用管理员单角色登录和服务端授权；管理员账户创建、停用、凭据更新及恢复操作留审计记录。文件下载通过应用授权接口，不暴露 `DATA_DIR` 路径。
- 日志关联请求、任务和操作标识；不记录数据库密码、认证密钥、领星令牌、完整附件内容或不必要的个人信息。日志轮转和保留期由组织运维基线确定。
- 监测 API/数据库健康、Worker 心跳、队列积压及失败任务、磁盘空间、备份成功与复制延迟、证书到期和服务重启。备份或恢复校验失败须通知运维负责人并阻断“备份通过”状态。
- 发布后保留当前版本与上一发布包，登记版本号、迁移编号、发布人、时间、检查结果和回退/恢复决定。文件和数据库的历史版本按业务规则保留，不以清理释放空间为由删除有效历史。

监控工具、告警接收人、日志留存天数及证书轮换周期需接入组织现有标准；仓库没有规定具体产品或数值。

## 7. 建设与上线阶段

| 阶段 | 建设内容 | 退出条件 |
| --- | --- | --- |
| 0. 生产条件确认 | 指定主机及负责人、固定 DNS/HTTPS 证书、客户端范围、防火墙规则、独立备份介质、密钥托管、维护窗口、RPO/RTO | 生产环境决策记录完整，网络与存储可用 |
| 1. 功能与发布准备 | 按 M2/M3/M4 计划完成业务链路、增量迁移、受控模板、发布包和运维说明；更新 M4 计划及相关 API/业务/操作文档 | 自动回归通过，迁移可重复核验，发布包清单有效 |
| 2. 隔离验收 | 归档样本和隔离夹具验证旧数据兼容、M2/M3 独立性、M4 分票/占用/复核/更正、箱数与数量守恒、下载授权及故障恢复 | 文件视觉检查通过；接收系统实际导入通过；未覆盖项明确列出 |
| 3. 生产预演 | 使用生产候选发布包在隔离环境执行备份、迁移、升级、故障回退、独立介质恢复及第二客户端 HTTPS 验证 | 恢复报告通过，未决任务核对完成，操作人明确签收 |
| 4. 小范围上线 | 对一个获批真实批次进行 M2/M3/M4 闭环试运行；人工比对来源、确认版本、XLSX 和接收系统结果 | 业务负责人完成明确签收；关键数据对账无误 |
| 5. 稳定运行 | 按日备份、按月恢复演练、发布审批、监控告警、版本和业务证据归档 | 运行交接、告警责任和恢复值班安排落实 |

生产切换采用单批次、小范围验证。M4 草稿和资料可提前维护，但正式生成待复核发票必须满足计划定义的 M2/M3 前置条件。任何真实导入或人工签收尚未完成的范围继续标记待验，不以自动化测试代替业务签收。

## 8. 上线验收清单

- M2 未完成 M3 时仍可导出发货表；旧链接、历史文件及保存进度可查询。
- M3 可独立恢复逐箱草稿和确认；重量/尺寸/PO 缺项、箱身份冲突及实质版本变化按规则阻断或要求整组重核。
- M4 仅选择本周有效完整 FBA；跨原制表组选择、地址冲突、重复占用并发、取消释放、更正移交、失败重试和生成期间版本变化符合计划。
- 同构箱压缩行可展开还原；混装箱、不同箱规和超过十箱按逐箱事实导出；按 FBA 与商品对账，箱数、数量和总重无遗漏、无重复。
- 接收系统实际识别的箱数、商品数量、PO、价格币种、图片和销售链接与系统一致；文件布局通过视觉检查。
- TLS 由指定第二台局域网客户端信任；数据库只允许本机访问；目标主机整机重启后服务、登录、API、Worker 和任务队列正常。
- 完整备份复制到独立介质；从该介质恢复数据库和 `DATA_DIR`，校验新增档案、单据、历史文件和索引；恢复环境不产生领星请求或重复外部操作。
- 业务负责人对真实批次和文件给出明确签收；记录发布版本、迁移编号、文件哈希、未决事项和恢复演练数据。

## 9. 投产前待确认事项

1. 正式 Windows 主机型号/版本、CPU、内存、可用磁盘、UPS 与维护责任人；按 5 会话、1000 箱基准实测后确认容量。
2. 固定 DNS 名称、证书签发与轮换责任、允许访问的客户端网段及组织防火墙规则。
3. 独立备份介质/异地位置、传输和静态加密方式、恢复密钥托管人及取回流程。
4. 业务批准的 RPO、RTO、日志留存期、告警接收人和生产维护窗口。
5. M2 实际批次签收、M3 现场实物核对签收、M4 正式模板与接收系统导入确认；未完成前不声明对应业务范围已正式验收。
