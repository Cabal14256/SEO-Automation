# 已确认业务规则

## 本次发货分票与自动制表（2026-10-24）

新导入默认使用“本次发货自动整理”，在线与 XLSX 可只填写本次 FBA，以空白行分票。同一分段必须单国家，可跨店铺、渠道和目的仓；混国、重复 FBA 或已占用货件阻塞。仍可仅导入需求，再人工安排到“某月第几次发货”，取消周范围的筛选、新建和分组限制。

发货票号为 `YYYYMMDD-X-国家简写-票序`。编号日期默认上海当天，提交前可修改，与实际发货日期独立；X 按编号日期所在月全国家共用并发递增，各国家票序按来源分段顺序分别从 1 开始，英国用 UK。校验后分配，重试不重号、不改号。票、FBA 成员和来源顺序独立保存，票号不写入需求内容指纹或覆盖原内部箱码。

自动来源后台补全、提交需求、按票及店铺/国家/渠道分组、同步、校验与确认，关闭页面后继续。不同周或月份导入的兼容需求可进入同组。人工建立共用月次数计数器，首票、内部组和次数原子提交，不自动同步；新箱码按本次发货分配，追加保留旧码。发货表只包含明确关联成员；任一来源阻塞禁止整次正式导出。发布成功冻结来源组和成员安排，更正保存原安排、次数、票号、箱码与文件。历史未关联组不自动归次。详见[发货次接口](../api/shipping-runs.md)。

## 发票直接取数与人工箱规（2026-10-23）

取消实物箱确认功能及其发票生成门槛。新票从领星/M2 逐箱数据自动带入 PO、毛重和长宽高，允许在本票按箱修改、恢复自动值，保存原始来源与修改修订。生成时使用最终 PO、KG 毛重和 CM 长宽高；缺值、非正数、未知单位且无有效覆盖或不能安全写入 XLSX 的数值阻塞生成。M2 数量、箱归属、箱序和箱码校验继续执行。新规则覆盖下文历史阶段对“最终始终采用领星值”和“M3 整组确认”的要求，详见[箱规规则](./invoice-box-data.md)。

## 自动制表确认补充（2026-10-20）

用户已要求取消“确认说明”及重复勾选，在当前可见的校验步骤自动确认并分配编码。同步结束且状态读取成功、当前成员/需求/商品箱版本一致、无阻塞异常时执行；接收差异提示不阻止。服务端自动生成审计说明并保留操作者、时间和不可变确认；确认与分码同事务，已有有效事实不重复版本或箱码。成员分组、数量冲突的口径决定、箱身份映射、冻结更正及 M3 实物核对仍沿用各自规则。

## M2/M3 与首期单据规则（2026-10-19）

2026-10-24 接收差异提醒：只在领星 `shipment_status=CLOSED`（接收完成）且有效接收数量与原货件申报数量不同的时候提醒。未接收、接收中、取消及状态未知时不显示这类提醒，不用接收数量推断完成状态。同步快照增加可选 `shipmentStatus`，旧记录缺状态时按未知处理；历史提前生成的接收提醒在操作界面按当前规则重新计算。冻结行可使用最新同店铺/FBA 的领星候选接收状态及唯一完整商品身份匹配的接收量，与冻结原申报量比较；不采用新候选的准备量、箱数据或其他校验结果，不改写原确认、原文件或数量。接收差异仍是非阻塞提示，不改变准备量或原装箱。

本节按 2026-10-23 箱规变更更新，覆盖下文历史阶段状态。M2 保持四步制表，发货表与发票均不依赖 M3。首期“发票”唯一指丰信 B2B 单票 XLSX，页面称“发票与单据”；独立商业发票及其他报关文件不在本期。

选票单位为本次发货的完整 FBA，可跨原制表组，不按原五箱假定分票。不同店铺、业务渠道、目的仓/地址、主体、币种、税务或模板分别出单；地址来源冲突须明确选择并记录原因。草稿可缺项保存；生成必须具备有效 M2 确认、箱码、完整有效的最终逐箱数据及代表商品申报资料。2026-10-24 新票规则 v2：商品使用完整平台身份匹配，申报单价取领星 Listing 普通售价的 20%，Decimal 四舍五入两位并自动采用，不换汇；旧 v1 人工确认价格仅保留历史兼容。

逐箱事实是实际箱数、商品数量和毛重的计算基础。同一 FBA 仅在完整箱内容及重量尺寸等一致、箱序连续时压缩编号范围。v2 每个输出编号仅保留按 MSKU/FNSKU/SKU 固定排序的首个代表产品；J 列默认用其标准箱规件数，缺失时用全箱实际件数合计。混装及默认数量与实际不同均提醒导出后手改；F15 与下游仍使用实际数量。重量按内部箱 ID 去重，不能按商品行重复计重。十箱以上同样按实际箱序处理。坐标和必填映射见[字段说明](./field-mapping.md)。

同用途 `SID + FBA` 并发唯一占用；取消释放，更正原子移交。单据修订、资料、模板及文件不可变，复核绑定具体文件哈希和依赖。提交、执行与发布均检查版本，业务阻塞 422，版本冲突 409。成功发布后才冻结来源组，失败不冻结；上游变化使现有复核失效，历史仍保留。外部接收系统导入及人工签收单独待验，不因技术测试通过而自动完成。

版本：1.9。更新日期：2026-10-18（`Asia/Shanghai`）。T09及T10–T11需求确认沿用；T12周批次与M2只读同步、候选修订、确认编码和成品表能力已实现。M3按《M3 历史计划》收口取值、舍入、缺项、核对及版本规则，独立实物确认和标准明细已进入技术验收。至少20票代表性真实货件、真实增量文件与业务逐行签收仍按实际证据分别验收，不把代码完成等同业务验收。

本文件是发货表格与箱数据模块的业务规则基线。规则分为已确认、待领星样本确认和待业务确认三类。已确认规则进入实现与验收；待确认规则不得被代码默认推断。

## 历史规则：M3取值依据与确认规则（2026-10-18）

本节仅解释旧 M3 记录与文件；当前发票不要求执行该流程，取数和人工修改采用本页 2026-10-23 规则。

本轮决定来自用户明确回复，附件《受控参考文件（不公开）》和示例物流商B2B模板用于核对字段及现有流程。附件示例包含`U000001-`写法，当前公式以用户明确给出的`000001-`为准，不自行增补`U`。单FBA存在不同箱规、重量或配方时，仍逐箱保存事实；箱范围显示标记不授权把这些箱合并为一条相同测量记录。

已复核[官方装箱接口](https://apidoc.lingxing.com/new/api-docs/FBA/ListShipmentBoxes/)：可取`weight/weightUnit`、`length/width/height/lengthUnit`及`quantityInBox`，本地既有真实样本也已取得LB/IN值。接口提供领星登记数值及单位，没有提供现场测量来源、测量设备精度或独立“已实测毛重”证明。API文档把返回字段列为必填，不等于M3业务表单必填规则，也不能保证每票实际返回都完整。

《M3 历史计划》确定：重量按毛重，来源采用领星登记值，现场实测独立留痕；KG/LB、CM/IN用Decimal换算后ROUND_HALF_UP到两位，不另设差异容差。必要重量、尺寸须为有效正数且单位受支持，Reference须有效，缺值／非法值／未知单位阻止最终确认，不补零或反推箱规。

逐箱保存草稿，全部箱完成后整组确认。一致仅记录核对事实，不伪造实测；有差异时至少填写一项不同的实测值及原因，最终仍采用领星值。未完成差异可暂存草稿，不能确认。箱身份、商品或数量不符不能用备注豁免，须转回M2映射／更正流程；M3同步不发布M2候选，不影响原发货表导出条件。

业务指纹包含箱成员、商品数量、两位KG/CM、Reference及缺项状态，不含任务号或采集时间。发现实质变化后暂停新确认／导出，采用后整组重核；等值重采保留进度。确认后修改实测记录使原确认过期，新记录保留且全组回到待核对。冻结且未被替代组允许补做M3，被替代旧组只读；修订、确认及文件历史保留。

M3本期提供三表标准实物箱明细XLSX，完整示例物流商B2B仍属后续单据模块。SOP中的渠道、VAT和分票说明作为后续单据配置依据；生成领星发货单、分配或补录库存等操作不构成本轮API写入授权。接口和状态见[M3 API](../api/physical-review.md)，真实批次逐箱核对与人工签收仍为pending。

## 子批次结构

```text
某月第几次发货
  ├─ 子批次 A：成员 FBA 集合，3 箱，A1-A3（虚构示例）
  └─ 子批次 B：另一成员 FBA 集合，2 箱，B1-B2（虚构示例）
```

以上虚构的 A/B 两组即使商品身份、店铺、渠道和日期相同，只要 FBA 集合不同，也保持独立子批次；同一需求全局仅一个有效组和一个发货票占用。

## 真实样本支持的实现约束

本节约束数据处理方式，尚需在正式业务模块实现。详细算法和公式见 [US 箱分配与编码算法](./us-allocation-algorithm.md)，证据与覆盖边界见 [2026-10-16 验证记录（私有研究说明）](../research/README.md)。

- **分组先于配方归并。** 同商品、同日期、同目的仓也可能属于不同STA计划；候选组经人员确认后才能参与统一编码。STA计划不直接等于业务子批次，按同sid、国家和业务渠道的人工边界允许跨计划合组和同计划拆组。
- **单票和同组均允许多配方。** 保留每个实际箱与商品关系；只有所有箱配方一致才采用“单箱数量 × 实际箱数”简写。通用汇总始终为逐箱求和。
- **配方比较保留频次。** 商品身份按固定文本顺序规范化；箱方案用配方多重集比较，忽略箱返回顺序但保留每种配方的箱数，不能用去重集合丢掉实际箱。
- **编号域分开。** 平台箱 ID、货件内 `localBoxId`、箱名 `box_name/boxName`、内部箱 ID 与展示编码分别保存。箱名可不连续，本地序号可以从 1 重复开始；不以数组位置或箱名代替永久内部 ID。
- **数量口径分开。** 运营参考需求、详情申报、列表当前/初始申报、装箱合计、本地已发货和已接收分别保存。当前正式主数量为详情quantity，装箱不守恒阻塞；列表冲突须记录人工决定。少收/多收单列差异，不反向改变原装箱，真实业务签收仍待补齐。
- **缺值不补零，重复不静默删。** 不完整分页、缺身份、缺数量或不明货件归属先阻塞；明确返回的已发货/接收量 0 有效。完全重复记录保留源行，去重结果只用于差异诊断，实际处置需人工确认和版本审计。
- **日期和渠道保持来源。** 创建日期、计划发货日期、送达窗口及业务日期分开；送达窗口跨周不自动拆组。承运编码/Other 不替代 示例渠道A/示例渠道B/示例渠道C 等业务渠道。
- **重量尺寸保留单位和版本。** LB/IN 不直接当作 KG/CM，登记值、实测值和确认值分开；历史表“重量”汇总列不作真实箱重。
- **同步不改变确认事实。** 查询失败与不存在区分；缓存标明原采集时间。刷新不能静默重排、覆盖确认值或重发旧箱码，异常按子批次隔离。

已验证的STA样本支持上述处理约束，不代表生产验收。本轮已明确详情quantity主口径、人工箱序、计划与业务组关系及动态箱列输出；真实跨次箱标识稳定性、未覆盖国家/非STA和真实业务签收仍须补证。

## 状态建议

```text
待分组 → 待同步 → 同步完成 → 有差异 → 待人工确认 → 已确认 → 可导出 → 已导出 → 已打印
```

异常状态、人工处理、版本冻结和外部同步结果必须保存操作人、时间、原值、新值、原因和关联文件。

## 待确认规则

- 既有货件改店铺/FBA身份的专门更正流程；当前导入不得改绑已提交源行或自动改变已确定的发货次归属。
- 旧周日期仅作历史兼容元数据；当前发货次用稳定 UUID，不使用显示名称作主键。
- 平台箱标识跨次及修改装箱后的真实稳定性；人工映射和箱序策略已实现，已观察到的boxName别名不再属于未取得字段。
- 详情主数量、列表冲突决定和接收差异分栏的真实业务对账签收；不得以技术夹具代替。
- 有效期、包装、标签/预处理所有方是否纳入生产配方兼容条件。
- 超十箱、混装和商品跨箱的成品表版式已选动态箱列加逐箱长表，仍需业务人员核对正式成品。
- 旧M3历史的现场核对及签收仍按真实证据保留待验状态，不成为新发票前置条件。M2制表确认不等同线下实物核验，物流模块独立线下复核要求继续保留。
