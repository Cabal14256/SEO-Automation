# 月内发货次与分票

在线填写或上传单列 FBA 清单，每票之间使用空白行。现有多列导入模板仍可使用。首尾空行忽略，连续空行合为一次分隔；缺少 FBA 但填写了其他业务字段的行需要修正。在线草稿保留空行和编号日期。

编号为 `YYYYMMDD-X-国家-票序`。编号日期默认上海当天，X 按该日期所在月份全国家共用并发安全地递增，各国家票序按来源分段顺序分别从 1 开始，英国使用 UK。编号日期与实际发货日期分别保存。混合国家分段和重复 FBA 阻塞整理，不自动拆票或删除。

业务时间统一为“某月第几次发货”，每月次数不限。人工建立和自动整理共用月计数器；不同周或月份导入的需求可安排到同一次发货。首次业务日期仅作不可变来源事实，不限制发货归属。

## 接口

以下接口位于 `/api/v1/shipping-runs`，仅有效管理员可用。

- `POST /`：传入 `operationId`、`importId`、`parseRunId`、可选 `numberingDate`，接收后台整理任务。相同操作与内容重试返回同一记录。
- `GET /`：按接收时间倒序返回发货记录。
- `GET /:id`：返回 `run`、`tickets`、`issues`。任务包含版本、阶段、状态、编号日期和月内次数；票包含来源分段、国家、票号及成员顺序。
- `POST /:id/retry`：传入 `operationId`、`expectedVersion` 恢复失败或待处理任务。编号及需求提交前可传入修正后的 `importId`、`parseRunId` 替换来源；编号后保持票成员，使用原批次的版本化处理流程解决异常。
- `POST /manual`：传 `operationId`、可选 `numberingDate`、`name`、`reason`、`demandIds`、`expectedDemandVersions`，同事务建立人工发货次、首票、内部组并领取月内次数；失败不消耗次数。人工 `origin=manual`、导入引用为空，初始 `draft/sync`，不会自动同步。
- `POST /:id/tickets`：提交名称、原因、需求及版本，另含发货次 `expectedVersion`，增加一票。人工创建及此接口可同时传 `existingGroupId`、`expectedGroupVersion`，显式关联完整未冻结历史组，由新容器替代组重新确认及编码，不按历史日期推断归属。
- `POST /:id/tickets/:ticketId/members`：传 `operationId`、发货次 `expectedVersion`、`groupId`、`expectedGroupVersion`、原因、新增 `demandIds` 及其版本，向兼容组追加。保留原成员、票号和顺序；新增列表不用于隐式删除旧成员。
- `POST /:id/correction`：传 `operationId`、`expectedVersion`、`reason`，完整快照保存至 `shipping_run_correction` 并解除成员冻结；月份、次数、编号日期及原票号保持。冻结内部组仍通过原更正流程修改。
- `GET /api/v1/batch-reports?shippingRunId=:id`：返回本次票成员的确认投影；尚未完成的内部组列入 `blocked`。票号、原内部箱码和来源版本分别保留。
- `POST /api/v1/batch-reports/exports`：在原导出参数中增加 `shippingRunId`、`expectedShippingRunVersion`，提供全部来源 `groupIds` 和 `expectedConfirmations`，`region` 为 `all`，不使用月份或区域裁剪。全部就绪且版本匹配才接受整次导出；发布成功才冻结来源组。
- `GET /api/v1/batch-reports/exports?shippingRunId=:id`：查看该发货次的文件和失败记录。

## 后台与异常

后台依次执行资料补全、需求提交、按票建立内部组、商品与装箱同步、校验和确认。页面关闭后继续处理。阶段请求及操作编号持久化，重启和重试沿用既有编号及成功结果；同步使用现有逐项恢复能力。

前台按真实整理阶段显示步骤，并按已确认来源关联统计就绪 FBA 数量。任务仍在排队或处理中、且处于分组／同步／确认阶段时，来源尚未确认或尚未分配箱码只作为正常进度；已完成内容可先预览。待处理、失败、已就绪后仍存在的阻塞，以及确认失效等其他异常继续展示具体票／FBA 和处理入口。整次导出仍要求全部来源确认有效，没有阻塞。

一张自动导入的业务票可包含同国家多个店铺或渠道，内部组按票、店铺、国家和渠道划分，不按导入周拆组。人工组保持店铺、国家和渠道兼容。新箱码前缀按发货次分配，追加保留原码；历史冻结组原码、确认和文件不改写。票号不写入需求内容指纹。发货表只包含本次明确关联的成员。

排队、运行、导出中的发货次不能修改成员；整次导出发布成功后冻结成员安排，修改前先显式更正。写入以原 `operationId` 和完整 payload 重放，版本冲突重新核对。人工草稿沿用处理向导手动同步和确认，全部有效后可导出；显式 `retry` 可继续后台同步确认，人工来源不接受替换导入。

发货表预览与新生成的 XLSX 按有效内部箱码的数字序号放置数量，例如 G7、G8 的数量分别进入“箱7、箱8”，G9、G10 对应“箱9、箱10”，不在每个 FBA 重置展示列。展示箱列 `displayBoxOrder` 与货件内箱序 `boxOrder` 独立保存，逐箱明细同时列出两者；作废或未使用的箱码序号保留空列，不将数量左移。不同字母前缀各自使用对应数字列，完整箱码和 FBA 保留以区分来源。

预览与新生成的 XLSX 按每个 FBA 的最小内部编码排列完整 FBA 块，字母前缀依次为 `A…Z、AA、AB…`，同前缀按数字升序（例如 `A2` 排在 `A10` 前）；每个 FBA 的商品按首个正数量所在展示箱列升序排列，同首箱保持来源商品顺序，无正数量的行置后。每行编码列表及逐箱明细使用相同编码顺序，预览在分页前完成排序。箱码及实际分箱数量保持原确认事实，超过 10 箱继续向右扩展；历史已发布文件保持原样。

未找到货件、店铺或渠道歧义、混国、重复或占用、数量冲突、箱身份问题及版本过期会暂停并给出定位。未编号时可用“修正清单并继续”在线调整或重新上传来源；已编号时在相关批次解决问题，再继续整理。丰信发票的合票与生成规则不变。

## 验证入口

`scripts/t39/shipping-runs-browser.mjs` 使用离线模拟 API 验证导入、分票预览、后台进度、12 箱显示、手动导出和历史恢复。服务端 `modules/shipping-runs`、导入解析和报表模块包含编号、并发、恢复及导出范围测试。测试使用虚构 FBA，不调用真实领星业务数据。
