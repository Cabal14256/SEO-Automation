# 验收场景

## 月内发货次替代周范围（2026-10-24）

1. 所有日常筛选、新建、追加、发货表、发票候选及工作流摘要显示月份和发货次，无周范围入口；跨周及跨月导入的兼容需求可进入同票同组。
2. 人工首票、内部组和月次数原子成功，失败不留空发货次、不消耗次数；同月并发、跨月重置及原请求重放正确，人工建立不自动同步。
3. 新箱码在本次发货内分配，追加保留旧码，分组更正同步调整票成员关联；跨发货次合并/移动拒绝，并发占用一个需求仅一个成功。
4. 冻结成员安排先保存更正快照，次数和原票号不变；导出中的成员不能修改，历史确认、冻结码和已发布文件保持原样。
5. 历史未关联组不根据周日期自动编号，显式关联未冻结完整组后重新确认编码；新发票只读取所选发货次的明确成员，不混入同历史组的其他货件。

## 五步导入向导（2026-10-18）

以下为本轮回归场景，测试正在执行，不提前登记通过数量。UI 脚本为 [`scripts/t25/import-wizard-browser.mjs`](../../scripts/t25/import-wizard-browser.mjs)，使用独立 Vite 与内存 HTTP fixtures，不读业务库或调用领星；报告/截图默认写入 `.local/t25/frontend/`。真实集成与业务签收分别保留结论。

1. `/imports` 的“导入”统一进入选择方式、填写与解析、确认店铺、核对与提交、导入结果五步；文件上传和网页在线表格共用后续流程。上传/保存成功停在源行核对，不直接提交或跳入结果页。
2. 解析中、工作表待映射、解析失败或源行读取失败时不能越过第二步；修正/重试后读取最新源行。第三步至少确认一家有效店铺才能生成预览，成功后才进入第四步；未确认店铺的错误不阻止其他有效票部分提交。
3. 第三步不常驻显示差异与提交操作；第四步保持分类筛选、跨页选择和逐票变化确认，错误/冲突不可提交。预览/提交执行中暂时锁住步骤导航，迟到响应不能把用户带回已离开的流程。
4. 关闭重开同一向导保留当前未保存单元格/`File`；刷新后仅恢复已接收导入的 ID、阶段和核对版本，未保存输入需重新填写或选文件。普通勾选刷新后重新核对，不误称为持久草稿。
5. 预览或提交返回已知 409 时留在当前核对阶段并保留选择/提示，可返回确认店铺重新生成；不同版本、历史解析和未完成源行核对不能新提交。
6. 提交已落库但响应丢失、响应不可识别或结果未知时，保留原 payload 和 `operationId`；目录/解析变化、关窗重开或刷新后，“重试原提交”仍重放原请求。同操作的提交记录可直接恢复成功；不得以另一最新操作替代本次结果。
7. 另一窗口重新解析后，显示“核对最新解析版本”，在重新读取并核对源行前禁止新预览和普通提交；恢复原未知提交仍可使用其原操作号。旧预览不随目录焦点刷新静默切换。
8. 导入记录和 `/imports/$importId` 详情均可“继续导入”，`/imports/new?importId=<导入UUID>&step=1..5` 的深链不能绕过前置检查。恢复详情、店铺确认或提交记录失败时显示可重试反馈，不无限等待或假设无历史。
9. 部分提交和此前已提交导入可恢复结果、查看来源并继续处理；“有效项已提交”时错误/冲突仍有继续入口。原件、历史解析、需求版本及提交来源保留，参考数量不转作正式商品数量。
10. 在 320px、390px、768px、1024px 和宽屏核对向导边界、横向滚动、步骤状态、Esc/关闭重开、焦点恢复及减少动态效果偏好。

## M1 发货次与需求导入

T10–T11确认规则：货件级需求以sid＋标准化FBA唯一；相同只补来源，五个业务参考字段变化必须显式确认版本；本次候选店铺选择不批准全局别名。错误/冲突不能提交，但可选择其他有效票；选择范围全事务回滚。参考量不作正式商品量，缺失仅按人工选择的历史基线提示。当前T12分组与完整M1端到端仍待实现。

1. 以 `Asia/Shanghai` 的编号日期确定发货月份，人工与自动共用月内次数；同月多次、并发、跨月和跨年重置正确。
2. 不同周或月份导入的兼容需求可进入同一次发货及同一内部组；票、需求与内部组关联准确。
3. 来源没有子批次标识时，系统必须进入人工分组，不能自动合并。
4. 子批次默认按最小标准化 FBA 号排序，人工调整后保存排序版本。
5. FBA 号去首尾空格并转大写；纯文本排序；领星不存在的 FBA 返回错误并阻止同步。
6. 同一需求全局只能属于一个有效内部组和一个发货票；跨发货次并发占用只允许一个成功。
7. 已确认子批次可以追加 FBA；旧编码不变，新箱使用后续编码。
8. 子批次可以人工合并、拆分和移除 FBA；每项操作产生新版本并保留审计。
9. 已导出或已打印子批次禁止移动、合并、拆分和追加。
10. 重复导入、同一 FBA 多商品、每日追加、数量减少、跨月重复和错误源行均可定位。
11. `sid + sta_inbound_plan_id` 仅提出候选分组，必须由人员确认业务子批次；相同商品、配方、日期、目的仓或送达窗口均不能独立触发合并。同一业务子批次是否允许跨多个 STA 计划仍待业务确认。
12. 分组和汇总不固定为每组五票、每票两箱；按实际 FBA 和箱记录计算。首次业务日期、发货次编号日期、实际发货日期和送达窗口分别保存；安排发货不改变来源日期，也不从送达窗口或旧周自动推断归属。

## M2 领星查询与发货记录

1. 输入有效 FBA 号和 sid，取得 MSKU、FNSKU、品名、SKU 和货件数量。
2. 输入领星不存在的 FBA，在确认店铺、查询日期及分页范围完整后返回明确错误，不生成空白货件；连接超时、授权错误、分页未完成或查询范围不符不得误报为“货件不存在”。
3. 多箱、混装箱、同一商品跨多个箱均能重建箱与箱内商品关系。
4. 商品总量等于所有箱内该商品数量之和；不一致时子批次进入异常并阻止正式导出。
5. 同一完整记录重复时阻止，并支持合并、删除、保留说明、修改数量后重新生成。
6. 不同 FBA 的相同商品和相同配方不误判为重复。
7. P/Q 类两个 FBA 集合不合并，各自保留箱数和编码范围。
8. 按本次发货和确认子批次生成 `A…Z、AA…` 编码，追加不重排旧码。
9. 正常子批次可以导出，异常子批次不能导出；同次发货其他子批次不被连带阻塞。
10. 导出文件引用已确认版本，保存文件哈希、数据版本和导出时间。
11. 商品匹配在店铺和货件作用域内保留 MSKU、FNSKU、SKU；算法以完整身份组合核对，不能按品名、商品返回顺序或单独 SKU 合并。身份缺失或同一身份映射冲突时进入待处理状态，不猜测补齐。现有探测报告的 MSKU + FNSKU 数量核对不能替代这一生产验收要求。
12. 箱配方比较完整商品身份及箱内数量，忽略商品返回顺序；货件配方比较箱配方的多重集，忽略箱返回顺序但保留每种配方的箱数。两个相同配方箱必须计为两箱，不可用集合去重；单箱总件数相同也不能判定配方相同。
13. 同组一票一箱、另一票三箱时，分别保留实际箱数并按确认组汇总；虚构的两箱各 12 件但组成不同时，保留不同配方，不套用统一配方乘法。编码按实际箱记录生成，不按配方种类数生成。
14. 申报量、初始申报量、本地已发货量、接收量和装箱合计分别保存。装箱与业务确认对照量的差异进入准备异常；探测暂以详情申报量诊断，正式主口径待定。少收/多收单列接收差异，不反向修改原申报或箱配方，后续处理保留人工确认。
15. 完全重复来源行显示源文件、工作表、行号和差额；“去重后吻合”仅作为诊断，不自动改写原表或确认数量。使用虚构样例验证来源 30 件、申报 24 件、诊断去除一条重复 6 件后吻合；等待人工确认处理方式。

## M3 箱数据确认

当前实现与验收入口见[M3技术交付（私有记录说明）](./evidence/README.md)。本期已确定 ROUND_HALF_UP、必要字段缺项阻塞、无额外容差、部分差异只填差异项、Reference 单个可信来源可用且两非空必须相符；旧场景中“尚待确定”的文字作为前期记录，不再代表规则未定。技术夹具和真实归档复算均不替代现场逐箱签收。

1. 真实 API 返回的箱标识、箱名和接口顺序可以映射到稳定内部箱 ID；跨次刷新和修改装箱后的身份稳定性须单独验证，不能凭一次快照宣称稳定。
2. 箱号缺失、空装箱、分页不完整进入明确异常状态；非 STA 货件验证详情/装箱兼容性和降级路径，不能假定与 STA 相同。
3. 领星原始快照、人工补录和确认值分开保存。
4. 并发修改同一版本返回冲突，不覆盖他人确认结果。
5. 确认人、确认时间、数据版本和数量差异可追溯。
6. 同时兼容箱名 `boxName`、`box_name`，保留原始键；旧报告只检查 `box_name` 导致的空值提示不能当作真实缺箱名。`localBoxId` 的货件内序号与 `P1 - Bx` 平台箱名分别保存，不要求二者相等或平台箱名连续。
7. `localBoxId` 可在不同 FBA 重复；箱标识必须关联 sid、FBA 和内部箱 ID，保留 `boxId/packageId` 候选。跨 FBA 相同箱序号、商品或配方不合并箱记录。
8. 箱重、尺寸保留原数值与单位；LB/IN 转 kg/cm 时保留换算前后值及展示精度，不能将 LB、IN 数值直接标为 kg、cm。
9. 保存原始快照、规范化结果、配方指纹、确认版本和编码版本。重复读取、追加、删除或修改装箱后进行版本差异比较，不能仅按接口数组下标覆盖已确认箱；已导出/打印数据按既定冻结规则处理。
10. 按2026-10-18用户决定，货箱重量采用实测毛重业务口径，来源及与另行线下实测冲突时均以领星登记值为准。保留原值、原单位及差异；只读API返回不自动标记已完成实测，复核记录独立验收。
11. 示例物流商模板输出KG/CM，用户已确认重量与长宽高均显示/输出两位小数，保留原始值及原单位，不在中间步骤先行截断；使用LB/IN真实样本验证显式换算。接口number类型和示例小数位不代表测量精度；舍入方式、缺值/非法值与复核必填条件未确定前，对应部分保持待验，不能将位数已定标成换算功能已完成。
12. PO Number逐FBA取Reference ID，保存`reference_id`及`amazonReferenceId`原始来源；验证多FBA映射、缺失及来源冲突。当前原始快照归档不计作PO规范化或导出完成。
13. 用户确认货箱编号为`FBA号 + "000001-" + 该FBA实际箱数`，严格沿用本次公式，不自行加`U`。同一实际箱的多商品行不重复计箱，不将商品数量当箱数；不同箱规/重量/配方的逐箱事实继续保留，FBA范围标记不替代内部箱UUID或发货次内编码。以上为新增待验场景，不表示B2B输出已实现。

## API 样本覆盖

至少覆盖一票 STA、一票非 STA、一票多商品多箱、一票混装、一票商品跨箱、一票缺字段和一票接口失败。每类记录原始响应、规范化结果、异常处理和预期输出。

公开仓库不包含真实账号覆盖表或货件清单。使用虚构夹具验证单商品、多商品、多箱、混装、商品跨箱、同配方不同分组、重复记录、接收量差异、缺字段和接口错误；数值与身份均独立编造，不冒充真实取数证据。

实际验证须另行覆盖非 STA、箱标识跨次稳定性、装箱变化、多页完整性、限流恢复和 token 续约。每次记录新请求、缓存复用和离线重算，不把缓存当新样本，也不从少量成功查询推导固定 QPS 或长期配额。
